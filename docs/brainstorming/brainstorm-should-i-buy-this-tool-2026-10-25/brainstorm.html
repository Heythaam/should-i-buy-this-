Technique 01 · First Principles Thinking

Dig to the Bedrock, Then Rebuild

Strip the idea down to truths that can't be argued with — then construct upward from them.

▾ Ten truths, layer by layer, down to bedrock ▾
01A verdict is a probabilistic judgment from evidence; it does not need fresh computation every time for the same product.
02Scraping method is incidental; the real goal is a stable fact set of price, specs, and reviews.
03Reddit relevance is a retrieval and ranking problem, not a search-harder problem.
04Information in thousands of reviews lives in the distribution and outliers, not every individual review.
05The LLM is a reasoning and formatting layer, not a research layer; never ask it to know things, only to reason over supplied evidence.
06A product URL is just one identifier among many for the same real-world product.
07JSON cleanliness is a contract and validation problem, not a prompting problem.
08Confidence is a measure of evidence quality and quantity, not sentiment intensity.
09Wait verdicts are only meaningful with a time dimension, such as price history.
◆ Bedrock ◆ The atomic units of this system are Identity, Price, Opinions, Alternatives, and Reasoning — everything else is plumbing.
▴ Rebuilt upward: 15 ideas constructed from bedrock ▴
IDEA #20

Decouple evidence gathering from verdict synthesis via a fixed JSON evidence schema; the LLM only ever sees that schema, never raw HTML or text.

IDEA #21

Canonicalize every product by brand, model, and category before scraping alternatives or searching Reddit, so everything keys off one stable identity.

IDEA #22

Cache the full evidence bundle per canonical product for N days, since most incoming URLs duplicate already-researched products.

IDEA #23

Define a ProductPage interface with title, price, specs, rating, and review sample, and build thin per-site adapters behind it.

IDEA #24

Start a price-as-time-series table on day one, even with a single data point, so a wait verdict becomes a real statistical claim over time.

IDEA #25

Compute confidence as an explicit formula of review count, review recency, Reddit corroboration count, and spec completeness — not an LLM feeling.

IDEA #26

Enforce the LLM output via structured outputs or function-calling schema validation, never a "please respond in JSON" instruction.

IDEA #27

Build Reddit queries from canonical entity plus synonyms plus purchase-intent phrases like "anyone regret" or "worth it," not the raw product title.

IDEA #28

Solve review volume via stratified sampling of random, most-helpful, and one-and-five-star outliers, instead of summarizing everything.

IDEA #29

Treat official data providers like Rainforest API or Keepa as the true first-principles source of product data, with scraping only as a fallback.

IDEA #30

The real user need is a verdict, which a pre-built, periodically refreshed product knowledge base can serve instantly for popular products, instead of synchronous scraping.

IDEA #31

Design top-down from the UI contract: define the exact verdict JSON the frontend renders first, then derive what the LLM must output, then what evidence must be gathered.

IDEA #32

Separate fact fields like price and specs that must be exact from opinion fields like pros, cons, and verdict that are probabilistic, in the schema.

IDEA #33

Alternatives-finding is also a retrieval and ranking problem keyed on canonical entity, category, and price band — reusing the same infra as Reddit search.

IDEA #34

Store each verdict with a timestamp and product identity so repeat visits can show "the verdict changed since you last checked."

Technique 03 · Disney Method

Three Rooms, One Product

Dream without limits, build without excuses, then interrogate without mercy.

☁

Dreamer

No limits. No budget. No "but how."
  • ✦The tool watches a cart or wishlist across sites and proactively tells you when to buy, not just on demand.
  • ✦A browser extension overlay shows the verdict right on the product page itself, with no copy-paste of a URL needed.
  • ✦The verdict includes a short AI-generated voice summary you can listen to while shopping.
  • ✦Community-sourced trust scoring, where users vote whether past verdicts were right, building an accuracy track record over time.
  • ✦The tool tracks price drops and actively notifies "now is the time to buy," turning a wait label into a live alert instead of a static guess.
  • ✦A second-opinion mode runs multiple LLM personas — frugal engineer, luxury reviewer, sustainability advocate — each giving an independent verdict shown side by side.
  • ✦A visual evidence-trail UI lets you click any claim in the verdict and see the exact review or Reddit quote it came from, like inline citations.
  • ✦The tool builds a personal taste profile over time from what you bought versus skipped, and tunes future verdicts to that profile.
▣

Realist

Make it buildable. Make it ship.
  • ⚙Use a plugin architecture for scrapers — BeautifulSoup for static HTML sites, Playwright only for JS-heavy sites — selected by a per-domain config flag.
  • ⚙Use a job queue such as Celery, RQ, or Arq for the scrape, reddit, and LLM pipeline, so the API returns a job id instantly and the UI polls or subscribes for completion.
  • ⚙Store canonical product, evidence, and verdict in Postgres with a simple schema of products, evidence snapshots, and verdicts, versioned by scrape timestamp.
  • ⚙Use OpenAI structured outputs or a schema validation library with a retry-on-validation-failure loop to guarantee the final JSON shape.
  • ⚙Search Reddit via PRAW scoped to relevant subreddits plus a search fallback, then re-rank candidates by embedding similarity to the product title before the LLM sees them.
  • ⚙Pull the rating distribution the site already shows, sample fifty to one hundred reviews stratified by rating and helpfulness, cluster by embedding into themes, and summarize clusters rather than raw reviews.
  • ⚙Add a scraping proxy layer with residential proxy pool, user-agent rotation, and randomized delays from day one, since naive scrapers reliably work great for one week and then stop.
  • ⚙Build the FastAPI service as clear pipeline stages in separate async functions — extract, then enrich, then synthesize, then validate — each independently testable and mockable.
  • ⚙Use Jinja2 and HTMX for a simple reactive UI without a heavy JS framework, polling a status endpoint to progressively render sections.
  • ⚙Define the LLM verdict schema explicitly with verdict, confidence, pros, cons, alternatives, reasoning summary, and evidence sources, and version the schema as UI and prompt evolve together.
  • ⚙Separate the cheap extraction LLM calls for review clustering from the stronger synthesis LLM call for the final verdict, to control cost.
  • ⚙Add structured logging and per-stage timing and success-or-fail tracing from the start, since silent partial failures — empty reviews, zero Reddit hits — are the main debugging nightmare.
⚠

Critic

Where does this actually fall apart?
  • ✕Running headless Playwright at real scale is slow and resource heavy; a single always-on server will choke under concurrent requests without a worker pool or external rendering service.
  • ✕Residential proxies cost real money per gigabyte and add latency, so the anti-blocking fix carries its own budget and performance tax that must be sized against expected traffic.
  • ✕The LLM token cost for raw review text at thousands of reviews per product will balloon fast unless the clustering and sampling step is actually enforced in code, not just planned.
  • ✕Scraping Amazon product pages at scale may violate its conditions of use, which is a real business risk beyond personal or low-volume use, not just a technical hurdle.
  • ✕Reddit API terms and pricing changes restrict commercial use of PRAW-sourced data at scale, which is a real risk if a side project grows.
  • ✕Clean JSON still fails silently if the reasoning inside it is wrong but well formatted; schema validation catches shape errors, not substance errors.
  • ✕Caching evidence bundles risks showing stale prices or verdicts on fast-moving sale items, undermining the value of a wait recommendation.
  • ✕A generic fallback extractor for any e-commerce site is a much harder promise than it sounds, since unstructured pages can silently produce wrong specs or prices and erode trust faster than an honest "unsupported site" message.
  • ✕Confidence scores, however computed, mean nothing to users without calibration against real outcomes, or they are just another made-up number dressed as rigor.

  • #105Confidence scoring was independently rejected as an LLM judgment call in three separate techniques, all landing on an explicit outside formula — the most validated decision of the session.
  • #106Canonical product identity, evidence caching, and request coalescing are one system — a product-identity-keyed evidence cache — not three separate optimizations.
  • #107Multi-persona verdicts from the Dreamer room quietly solve the Critic room's hardest unsolved problem: persona disagreement is itself a usable confidence signal, not just a flashy feature.
  • #108Citations tracing every fact to a literal source quote, and the evidence-trail UI idea, are the same mechanism — grounding is enforced by requiring citations, then displayed as a feature.
  • #109Knowing when not to give a confident answer — via evidence sparsity state, fallback confidence downgrade, and an honest "unsupported site" message — may be the real product differentiator over raw verdict accuracy.
